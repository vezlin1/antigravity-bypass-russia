# Провайдеры DNS и наблюдение за моделью

Конфигурация `network.json` создаётся при настройке подключения:

- Windows: `%LOCALAPPDATA%\AntigravityBypass\network\network.json`.
- macOS: `~/Library/Application Support/AntigravityBypass/network/network.json`.

Служба читает настройки того пользователя, который включил обход. После изменения
провайдеров повторите настройку подключения, чтобы обновить системные правила DNS,
физические маршруты и закреплённые IP. Процесс DNS перечитывает список при запросах;
ответы из кэша предыдущей конфигурации не используются.

Для адресных запросов к доменам Agent быстрый обычный ответ Google остаётся
резервным до 300 мс, пока отвечают другие адреса того же DoH-провайдера.
Если приходит подходящий альтернативный адрес, он участвует в дальнейшем
подборе маршрута. Закрепление IP по-прежнему требует успешной проверки TLS/HTTP.
В резервных системных правилах сохраняются все настроенные UDP-адреса активных
провайдеров. Если подмена подтверждена, первыми указываются ответившие серверы,
за ними — остальные адреса тех же провайдеров. Повторяющиеся IP указываются один раз.

Пример настройки дополнительных провайдеров (адреса `.example` и `192.0.2.0/24`
демонстрационные, замените их своими):

```json
{
  "doh": [
    {
      "name": "my-doh",
      "url": "https://resolver.example/dns-query",
      "bootstrap": ["192.0.2.10"]
    }
  ],
  "extra_udp": [
    {"name": "my-udp", "addresses": ["192.0.2.20"]}
  ],
  "disabled_providers": [],
  "provider_order": ["my-doh", "my-udp"],
  "watch_region_errors": true
}
```

По умолчанию программа опрашивает DNS-AI и GeoHide EU по DoH. UDP-серверы
можно добавить в `extra_udp`.
У dns-ai.ru два bootstrap-адреса: `45.151.102.219`, `194.87.196.13`.
DoH endpoint: `https://dns.dns-ai.ru/dns-query`.
Для GeoHide EU используется `https://eu.geohide.ru/dns-query` с bootstrap-адресами
`217.60.245.219` и `217.60.245.233`. При обновлении со стандартной конфигурации
v2.5.0 этот DoH добавляется автоматически. Если вы меняли пул, порядок или
отключали провайдеров, GeoHide EU можно добавить в массив `doh` самостоятельно:

```json
{"name":"eu.geohide.ru","url":"https://eu.geohide.ru/dns-query","bootstrap":["217.60.245.219","217.60.245.233"]}
```
Поле `doh` заменяет стандартный список DoH. Чтобы оставить только UDP, задайте
пустой `doh` и добавьте серверы в `extra_udp`. `disabled_providers` отключает
указанных провайдеров. Хотя бы один провайдер должен быть включён. Имена уникальны
и чувствительны к регистру. В `provider_order` перечисляются предпочтительные
провайдеры, остальные следуют за ними. Если позиция `dns-ai.ru` явно не указана,
он остаётся первым. Подмена для конкретного домена имеет больший
приоритет, чем положение в списке: обычный ответ Google не вытесняет подмену.
При чтении старой конфигурации прежние стандартные списки bootstrap-адресов
заменяются актуальными. Имена удалённых встроенных Xbox DNS, Comss и GeoHide RU
убираются из порядка и списка отключений, если одноимённый провайдер не задан
в `doh` или `extra_udp`. Если старый файл содержит `"doh": []` и полагался на
встроенный UDP, сначала добавьте адреса в `extra_udp` или удалите поле `doh`, чтобы
включить оба стандартных DoH-провайдера. При настройке ранняя dev-метка удаляется
из `network.json`, чтобы файл прочитала v2.5.0. Настроенные серверы сохраняются.
Если активен GeoHide EU по DoH, при подборе маршрута Agent также проверяются
запасные TLS-адреса GeoHide.

DoH использует HTTPS с проверкой сертификата и имени сервера, без системного HTTP
proxy. Bootstrap задаёт адрес подключения, сохраняя имя сервера для TLS. Эти IP не
записываются как UDP nameserver. Если bootstrap-адреса молчат 750 мс либо все
завершились ошибкой, запускается одна попытка через системный DNS. Все попытки
ограничены общим сроком; проверка сертификата и имени сохраняется. Устаревший
список не должен отключать исправный DoH-сервер. DoH обслуживается локальной DNS-службой.
Если релей недоступен, Windows использует настроенные UDP DNS или проверенные
записи `hosts` для Agent. На macOS резервные UDP DNS должны быть настроены явно.
При обновлении уже действующих правил ошибка запуска или отсутствие пригодного
A-ответа на контрольные запросы останавливает настройку. Прежние правила DNS,
маршруты и настройки релея сохраняются. DNS-проверки Agent и Gemini/AI Studio
учитываются раздельно. На Linux настройка DNS требует работающей службы.
В прежнем режиме Windows IPv4 bootstrap и дополнительные UDP IP входят в
закреплённые физические маршруты. Без bootstrap разрешение имени DoH сервера
зависит от системного DNS.

### Автоматическое подключение Windows

Пункты **[1] Включить обход** и **[3] Настроить только подключение**, а также
команды `unlock` и `dns` на Windows используют системные маршруты для
DNS-провайдеров и сервисов. При переходе со старой настройки утилита
снимает свои закреплённые маршруты и проверяет подключение. Если проверка на
этапе подготовки завершается ошибкой, она возвращает снятые маршруты.

После включения или отключения VPN новые соединения используют маршрут Windows.
Фоновая служба сбрасывает кэш ответов и соединений DoH и подбирает замену
недоступным закреплённым адресам Antigravity. Если проверенные замены пока
недоступны, служба сохраняет текущие записи и повторяет проверку. При смене
сети во время запроса его может потребоваться повторить.

Пункт **[1]** запускает Antigravity App или IDE с локальным прокси в сеансе
текущего пользователя Windows. После включения CONNECT приложение можно
запустить повторно командой `antigravity-bypass-russia.exe --connect-launch app`.
Команда `antigravity-bypass-russia.exe --connect-launch web` открывает Gemini и
AI Studio в отдельном профиле Chrome. Обе команды запускаются без повышения прав.

Когда локальный DNS работает, прокси использует системное разрешение имён и
маршруты Windows. При блокировке локального DNS разрешённые AI-домены получают
запасное подключение через HTTPS DNS с bootstrap-адресами в маршруте VPN.
Перед передачей трафика прокси проверяет TLS-имя и доступность адреса через
текущий туннель. При отсутствии такого маршрута запрос завершается ошибкой и
может быть повторён после восстановления VPN. Правила Kill Switch остаются в
силе. Откат в пункте **[6]** выключает запасной путь для новых запросов.

Маршруты внутри VPN-клиента влияют на доступность серверов. CONNECT защищает
только управляемые сеансы. Сценарий, который лежит в основе решения, описан
в [issue #41](https://github.com/vezlin1/antigravity-bypass-russia/issues/41).

### Проверка на Windows 17 ноября 2026 года

При проверке из одной сети результат зависел от интерфейса. Через обычный маршрут
старые и новые UDP-адреса GeoHide возвращали адреса Google, совпадавшие с ответом
контрольных DNS. Через физический интерфейс, который выбирает утилита, оба новых
UDP-адреса не дали пригодного ответа в отведённое время.

| DoH через физический интерфейс | Cloud Code | Daily Cloud Code | AI Code | Generative Language |
| --- | --- | --- | --- | --- |
| DNS-AI | Подмена | Подмена | Обычный ответ | Подмена |
| GeoHide EU | Обычный ответ | Подмена | Подмена | Подмена |

На этом ПК все четыре выбранных узла прошли проверку сертификата своего домена
и ответили HTTP 404 на `HEAD /`. Контрольный порт релея 15353 отвечал, а локальные
пакеты UDP на порт 53 не доходили даже до отдельного тестового сокета. В таком
режиме Agent использует закрепления в hosts. Проверяйте браузерные сервисы
отдельно. Доступ аккаунта и результат генерации проверяются запросом в приложении.

При выборе закреплённых IP выполняются полный TLS handshake, проверка системным
хранилищем доверия, проверка имени и HTTP HEAD. Ответы 401/403/404 не означают отказ
TLS и не доказывают доступ к модели. HTTP 5xx, TLS alert, неверный сертификат и
таймаут исключают адрес. Старый IP проходит ту же проверку. При полном провале
подбора прежний файл `hosts` и сохранённый рейтинг остаются на месте. Два таймаута
не отличают устаревший IP от временного обрыва сети и не подтверждают рабочий
путь через системный DNS, поэтому автоматически снимать закрепления небезопасно.
Для daily и остальных обязательных доменов Agent нужны проверенные маршруты.
Обычный `cloudcode-pa.googleapis.com` можно пропустить при недоступности, если
сохранённые настройки обнаруженных клиентов явно указывают на daily и клиенты
закрыты. Для App значение `CLOUD_CODE_URL` на Windows должно совпадать в профиле
и в окружении программы настройки. Для IDE проверяется `jetski.cloudCodeUrl`
соответствующего продукта. При обнаружении CLI обычный адрес остаётся обязательным:
уже открытый терминал может запустить CLI со старым окружением.
При недоступности daily настройка останавливается до записи блока `hosts`,
рейтинга и правил DNS. Временные маршруты Windows для проверки откатываются.

При полном включении и настройке DNS endpoint приложения переключается на daily
только после успешного завершения настройки сети. Если проверка маршрутов или
применение DNS завершились ошибкой, прежний endpoint сохраняется. Команда
`patch-files` меняет только файлы приложения и не переключает endpoint.

Команда `report` добавляет `checks.dns_capabilities`: результат для каждого активного
провайдера и проверяемого домена Antigravity/Studio. Номер провайдера соответствует
`checks.configuration.active_providers`. Статусы `substituted`, `PASSTHROUGH`,
`sibling`, `unknown`, `no_addresses`, `timeout_or_error` описывают DNS-проверку.
Сравнение с эталонным DNS — эвристика маршрутизации, а не проверка модели или
аккаунта. Пользовательские имена провайдеров и URL не экспортируются.

`status`, экран меню, проверка подключения и `report` читают последние события
журналов при открытии. Наблюдение пассивное: оно не отправляет запросы модели и не
переключает маршруты. По умолчанию проверяются каталоги `logs` продуктов Antigravity,
Antigravity IDE и Google Antigravity в AppData/Roaming или Library/Application Support.
Массив `log_roots` позволяет указать другие абсолютные пути, в том числе журналы CLI.
`watch_region_errors: false` отключает чтение журналов.

Поддерживаются файлы `.log` и их ротации с `language_server`, `language-server` или
`antigravity` в имени, даты ISO и стандартные Go log timestamps. Учитываются события
за 15 минут: `StreamGenerateContent` с `ResponseID`, региональный отказ, требование
верификации и ошибка запроса. Начало ответа **не подтверждает завершение**. Старые,
неизвестные и не имеющие времени строки не превращаются в положительный статус.
Последняя ошибка отдельно сохраняется в сводке текущего временного окна, даже если
после неё зарегистрировано начало нового ответа.

Чтение ограничено числом файлов, размером и временем; неполный результат отмечается
`partial`. В отчёт попадают только категории и время событий, без строк журналов,
ResponseID, текстов запросов, токенов и путей. Поле `model_access` по-прежнему указывает,
что утилита сама не проверяла доступ; наблюдения находятся в `checks.model_observation`.
